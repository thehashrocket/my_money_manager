# my_money_manager — project guide for AI agents

Local-first, single-user personal budgeting app. CSV import from Star One CU (checking + savings). No cloud, no auth, no Plaid. The whole point is that **the user owns every sign on every row**.

Read `.context/notes.md` first if it is present. `.context/` is gitignored (it holds real bank-data samples), so it exists only on a machine where those artifacts were generated — a fresh clone will not have it, and that is expected rather than a missing file.

## Stack

- Next.js 16 (App Router, Turbopack) + TypeScript + React 19
- Tailwind v4 + shadcn/ui (base-nova style, Base UI primitives)
- better-sqlite3 + Drizzle ORM (`./data/money.db`, gitignored)
- Vitest for categorization/parser tests
- pnpm, Node 24 (pinned via `.nvmrc`, enforced via `engines` + `engine-strict`)

Recharts (`^3.10.1`) is in, powering `src/components/ledger/trend-chart.tsx` as of v0.7.0. Envelope cards are still plain CSS.

Wrong-Node symptom: any `pnpm` command fails with `ERR_PNPM_UNSUPPORTED_ENGINE` (blocked by `engines` + `engine-strict=true`). Run `nvm use` in the workspace to pick up `.nvmrc`. If you bypass pnpm (e.g., invoke `vitest` directly on Node 22), `better-sqlite3` crashes with a `NODE_MODULE_VERSION` mismatch because its native binding is built against Node 24.

## Scripts

- `pnpm dev` — start dev server (localhost:3000, this IS the app)
- `pnpm test` / `test:watch` / `test:ui`
- `pnpm db:generate` — generate Drizzle migration from `src/db/schema.ts`
- `pnpm db:migrate` — apply pending migrations
- `pnpm db:studio` — Drizzle Studio GUI
- `pnpm db:backfill-merchants` — renormalize `transactions.normalized_merchant` and rewrite the trained `category_rules` that key off it, after `src/lib/normalize.ts` changes. Dry run by default; `--apply` snapshots first and writes in one transaction. Two things refuse rather than warn, each with its own flag and its own exit code so they stay distinguishable: a collision whose rules disagree about the *category* needs `--resolve-conflicts` (exit 2), because that is the only part that moves money between envelopes; and a degraded snapshot needs `--allow-degraded-snapshot` (exit 3), because unlike `commitImport` this has no logical undo, so the snapshot is the only rollback path — usually the real fix is to stop the app container so nothing holds a read, not to pass the flag. Exit 1 is a post-write verification failure (`integrity_check`, `foreign_key_check`, empty keys, or any row whose stored key still moves under the normalizer). Runs inside the container (the live ledger is in the `mm_data` volume), so the image must be rebuilt from the branch carrying the normalizer change first. See rule 10.
- `pnpm db:seed-dev` — dev-only fixture ledger (`scripts/seed-dev.mjs`), never imported by the app. Exists because ~15 tasks in the liability plan verify "manually, with a mortgage present" and a fresh ledger has nothing to look at. Two guards, both load-bearing: it refuses without an explicit `DATA_DIR` (`dbPath()` falls back to `./data`, which IS the real ledger), and it refuses again if any ledger table has rows — the second check runs **before** `migrate()`, not after, because this script calls drizzle's migrator directly rather than going through `scripts/migrate.mjs` (rule 7), so a mistyped `DATA_DIR` would otherwise have already run rebuild migrations against the real ledger by the time the refusal printed. Run it as `DATA_DIR=./.context/seed pnpm db:seed-dev`.
- `pnpm simplefin:claim` — one-time: exchange a SimpleFIN setup token for an access URL (writes `.env.local`)
- `pnpm simplefin:sample` — dump a live `/accounts` payload to `.context/simplefin-sample.json` for analysis

## Docker (SQLite still — no Postgres yet)

`docker compose up` is a second way to run the app, alongside `pnpm dev`, not a replacement — see `docs/plans/dockerize-postgres.md` for the staged Postgres migration this sets up. The ledger lives in a named volume (`mm_data:/app/data`), not a bind mount: SQLite WAL-mode locking over VirtioFS/gRPC-FUSE (macOS bind mounts) is a known corruption hazard class, so `money.db` isn't directly visible on the host under Docker the way it is under `pnpm dev`. Snapshots land on a separate bind mount (`./backups`, `SNAPSHOT_DIR=/app/backups` in `compose.yaml`) so they survive `docker compose down -v`.

- `pnpm db:seed-volume` — **run once, before the first `docker compose up`.** Copies `./data/money.db` into the (currently empty) volume via `createSnapshot`'s `VACUUM INTO`, never a bare `cp` — the host DB runs in WAL mode, and a plain copy can silently drop rows still in `money.db-wal`. Refuses (rather than overwrites) if the volume already has a `money.db`.
- `pnpm db:export` — snapshots the running container's ledger (via `docker compose exec` + the bundled `scripts/snapshot-cli.mjs`) and copies the result to `./backups/`. Refuses to copy out a degraded (`consistent: false`) snapshot. Uses its own `EXPORT_PREFIX` (`src/lib/snapshot.ts`), not the pre-import prefix rule 5's automatic snapshots use — sharing a prefix would put a deliberate manual backup in the same retention-of-10 pool `commitImport`/`syncSimpleFin` auto-prune, so it could be silently evicted by ordinary use. Nothing prunes the export pool automatically.
- `pnpm db:import <file>` — stops the container, restores a snapshot file (must have no `-wal` sidecar — see rule 5), restarts.
- `docker/entrypoint.mjs`, `scripts/snapshot-cli.mjs` and `scripts/backfill-merchants.mjs` are gitignored **build artifacts**: the runner image has no `src/` tree and no devDependencies, so they can't stay thin wrappers around `src/lib/snapshot.ts`/`src/lib/paths.ts`/`src/lib/normalize.ts`. `scripts/build-docker-artifacts.mjs` (esbuild, `better-sqlite3` external) bundles `docker/entrypoint.src.mjs`, `scripts/snapshot-cli.src.mjs` and `scripts/backfill-merchants.src.mjs` into them during the Docker builder stage — edit the `.src.mjs` files, not the generated ones. A new bundled artifact means an image built before it exists cannot run its command; `db:backfill-merchants` detects that case and tells you to `docker compose build`.
- The container refuses to boot without `TZ` set (`compose.yaml` sets `America/Los_Angeles`) — the app derives the current budget month from local time (`src/lib/now.ts`), and Docker's default `TZ=UTC` would silently compute the wrong month for part of every day.
- The published port is loopback-only (`127.0.0.1:3000:3000`): this app has no auth, so binding `0.0.0.0` would make the ledger LAN-readable.
- **On real Linux hosts (confirmed via CI, not just theorized), `./backups` needs its permissions fixed BEFORE the first `docker compose run`/`up` of any kind — including `pnpm db:seed-volume`, which starts one itself.** It's a bind mount, and Docker on native Linux auto-creates a missing bind-mount host directory as root-owned; the Dockerfile's `chown` only affects the image filesystem, which the bind mount then shadows. Without this, the container's unprivileged `node` user gets `EACCES` on its first snapshot write and never becomes healthy. Fix: `sudo mkdir -p ./backups && sudo chmod 777 ./backups` on the host, first — before `db:seed-volume`, not after. `chmod`, not `chown` to a single uid: two different principals need write access to this same host directory — the container's `node` user (uid 1000) writing snapshots, and `pnpm db:export` running on the **host** (a different user entirely) copying them out via `docker compose cp`.
  This took three attempts to get right, each confirmed against a real CI failure (Ubuntu; macOS Docker Desktop's more permissive bind-mount layer never surfaced any of it): (1) no permissions step at all → `EACCES` on the container's snapshot write; (2) `chown 1000:1000` → fixed the container's write, broke the host's own `docker compose cp` copy-out (`unlinkat ...: permission denied`, since the CI runner user isn't uid 1000); (3) `chmod 777`, but placed *after* `db:seed-volume` → `db:seed-volume`'s own verification step starts a container from the full `app` service definition, materializing (and root-owning) the bind mount before the `chmod` step ever got a turn (`chmod: changing permissions of 'backups': Operation not permitted`). CI's `docker` job runs the corrected `sudo mkdir`/`sudo chmod` step first, before anything else touches Docker.

## Core rules baked into the data model

These are load-bearing. Violating them corrupts the database.

1. **All money is stored as signed integer `amount_cents`.** Never floats. Never a separate sign column. Withdrawals are negative. Deposits are positive. Balance = `starting_balance_cents + SUM(amount_cents WHERE date > starting_balance_date)`.
   The `>` is strict, which decides what a valid anchor is: `starting_balance_cents` must be the balance at the **close** of `starting_balance_date`, never its opening balance, or every row dated that day drops out of the total. A CSV import derives the anchor from Star One's running `Balance` column (persisted per row on `transactions.balance_cents`) rather than trusting the number typed at account creation — both real accounts were created with 0, which makes every displayed balance a net-change-since-signup figure and makes `/sync`'s drift check report a phantom missing row forever. `deriveStartingBalance` only writes an anchor when the file's running balance forms a consistent chain (that is how the true intra-day row order is established — Star One's export order is not a documented guarantee), and the anchor only ever moves **forward** in time: any (date, true closing balance) pair is valid, but a later one needs less history to be complete for the sum to come out right.
   A same-day transaction pair that nets to zero (a paycheck and a bill, say) makes the running-balance chain validate in **both** directions at once — nothing in the math says which order is real, and the two orders have been measured producing disagreeing anchors from the same file. `deriveStartingBalance` checks both candidate orders against each other in that case: if they agree on the resulting anchor it's used, and if they disagree it refuses rather than guess, leaving the existing anchor alone.
   `anchorStartingBalance` (`src/lib/importBatch.ts`) runs **inside** `commitImport`'s write transaction, not after it — a crash between the two used to be able to leave the imported rows in place with no matching anchor move and no record of what almost happened. It also bounds-checks a derived anchor the same way a hand-typed one is checked (`src/lib/import/accountAnchorFields.ts`, shared with `validateCreateAccountInput`/`validateUpdateAnchorInput`): a single-row file trivially satisfies the chain check, so one corrupted or hand-edited Balance cell no longer anchors the account on whatever that row says without corroboration, and a derived date in the future is declined for the same reason a hand-typed one is. Every anchor move persists the account's **prior** anchor value onto the batch (`import_batches.prior_starting_balance_cents`/`_date`), shown on `/import/success/[batchId]` so a bad automatic move can be corrected via the manual anchor form without guessing what the old number was; a declined move now surfaces as a warning on that same page instead of failing silently.
   The SUM excludes pending rows (`is_pending = false`). Star One's own running balance — the source of the anchor — doesn't reflect a pending row's amount until it posts, and the SimpleFIN `balance` field `/sync`'s drift check compares against is posted-only. `loadAccountBalances` and sync's `finaliseBalances` both filter on it; a pending row left in the sum overshoots the real balance and makes the drift check report a phantom missing row on every run.
   A bank figure being present doesn't mean it's current, though: SimpleFIN's `balance` carries its own `balance-date`, and when the connection stops refreshing, that snapshot simply stops moving — measured once at +$893.84 of "drift" that was really just a day of activity the feed hadn't reported yet. `classifyBalanceFreshness` (`src/lib/simplefin/balanceFreshness.ts`) only treats a non-zero difference as real drift once the bank figure's date is strictly *after* the ledger's newest row (or its anchor, when there are no rows after it); a same-day, older, or dateless bank figure renders as unconfirmed instead of accusing the ledger of a missing or duplicated row it doesn't have.
   **The feed's balance write is the one anchor path with no human in the loop, so it treats everything it read before the round trip as a PRECONDITION (v0.26.0).** `refreshLiabilityBalances` (`src/lib/simplefin/sync.ts`) judges the FEED's figure first — bounds, date validity, rule 9's sign guard — because none of that needs ledger state; everything that reads or writes the account row then runs in one per-account transaction that re-reads it. Three things are re-verified there and each was wrong to assume: that the account still exists, that it is still linked to the feed the balance came from, and that `hasAnyTransactionRows` is still false (a row imported during the fetch window makes the account ineligible for a feed-written anchor, and the pre-await answer could say otherwise). `prior_starting_balance_cents`/`_date` are taken from THAT re-read, never from the account row loaded before the fetch — a hand Reconcile landing in those seconds would otherwise be silently overwritten and have rule 9's single undo slot spent storing a figure that was already stale. The transaction returns what it actually did (`deleted` / `relinked` / `has-rows` / `no-op` / `written`) and only the `written` branch produces a `LiabilityBalanceUpdate`: pushing one unconditionally made `describeBalanceUpdates` announce "Balance updated: X is now $Y" for an UPDATE that matched zero rows — a fabricated durable fact, and `/sync`'s "a no-op is never reported as a completed action" broken on the one write rule 9 calls silent and expensive. The positive-card-balance remark moves with it, after the write rather than before, so a stable overpaid card stops rendering a permanent red error under its Refresh button.
   A wrong anchor is no longer a raw-SQL fix, either: `updateAccountAnchorAction` (`src/app/import/actions.ts`) plus `validateUpdateAnchorInput` (`src/lib/import/validateUpdateAnchorInput.ts`) give `/import` an inline per-account form to set `(starting_balance_cents, starting_balance_date)` directly — the only way back once `deriveStartingBalance`'s forward-only anchor has already moved too late. The date is capped at today: a future anchor would exclude every real transaction from the sum and permanently silence the freshness check above for that account too. The shared `startingBalanceDateSchema` (`accountAnchorFields.ts`) validates with `z.iso.date()`, not a bare `YYYY-MM-DD` regex, so a syntactically-shaped but calendar-invalid date like `2026-13-40` is rejected on every anchor-writing path (hand-typed and CSV-derived alike) rather than reaching the `>` comparison above, where SQLite's lexicographic TEXT sort would put it after every real date in the year and silently drop the account's entire history out of the sum.
   That same `startingBalanceDateSchema` check now also runs on every ordinary transaction row during CSV import, not just the anchor: `parseCsv.ts`'s `mmddyyyyToIso` previously only range-checked month (1-12) and day (1-31), which passes a calendar-invalid combination like `04/31` (April has 30 days) or `02/29` on a non-leap year straight through as a syntactically-valid but wrong ISO string. As of v0.12.4 that candidate string is validated the same way, and a calendar-invalid row is rejected with a `ParseError` instead of landing in `transactions.date` unvalidated.
   **"Spend" is a SIGNED sum, and what counts as spending is decided by `categories.kind`, never by the amount's sign (v0.19.0).** A refund reduces the category's spend — envelope budgeting implies it, since returning $20 of groceries restores $20 of grocery-buying capacity. `/budget`'s rendered spend (`loadSpendForMonth` → `loadMonthView.ts`) always worked this way; the dashboard's 6-month chart (`src/lib/trends/loadMonthlyTrends.ts`) did not, and the two disagreed live — September 2026 read $10.00 of Misc on `/budget` and $295.00 on the dashboard, the same category in the same month. Both are now `0 - SUM(amount_cents)`. They share an EXPRESSION, not one predicate: only the chart restricts to `kind = 'expense'` in SQL, because it aggregates across categories rather than being handed one; `loadMonthView` decides expense-ness by iterating `expenseLeaves`, and `computeMtdSpent` (which feeds the *rollover* chain, not the rendered figure) applies no kind filter at all. `leftToBudgetCents` is untouched by any of this, and NOT because it is computed from spend — it is `plannedIncomeCents - allocatedCents - plannedFundCents` and has no spend term, so no spend convention can move it. **An amount-sign predicate in this repo is never only a sign predicate.** `loadMonthlyTrends`' `amount_cents < 0` was doing two jobs: dropping refunds (the bug) and incidentally excluding every income row, which is positive. Deleting it alone pulls 43 paycheck/interest rows worth +$52,131.17 into the six-month window and draws them as ~$52k of *negative* spend, so it was replaced by an explicit `category_id IN (SELECT id FROM categories WHERE kind = 'expense')` subquery — check what else a sign filter is excluding before touching one. A month whose refunds exceed its spend reports negative rather than clamping to zero (clamping is the same class of lie), which is why `trend-chart.tsx` uses `stackOffset="sign"` and its tooltip keeps negative values; a group is dropped from a *month* whose net is exactly zero, while `categoryNames` keeps any group that draws in at least one month — those are different tests, and conflating them blanked two months of real activity (a charge in March refunded in April nets to zero across the window while drawing a real bar in both). "Is there anything to draw" now has one definition, `hasDrawableData`, in the read model rather than in `TrendChart`; `totalSpentCents === 0` is NOT it. **`src/lib/goals/loadGoals.ts` is deliberately NOT converted** — goal progress is `allocated − withdrawn`, and a *net* withdrawn figure would let a deposit into a fund increase progress on top of the allocation already counting the same intention. It stays outflows-only, with the analysis recorded in-code; do not "align" it without reading that. **`GoalRow.targetCents` is `number | null`, never coerced** — it was `number` with a `?? 0` until v0.23.0's review, which made `/goals` render "target $0.00" for a fund with no target (a claim that it is already complete) and prefill its Edit-target form with `0.00`, a value `updateGoalTargetSchema`'s `.positive()` then refuses — so submitting the value the form itself supplied took out the page via `error.tsx`. `FundRow.targetCents` on `/budget` had the nullable version and rendered an em dash, so the two surfaces disagreed about one column and the coerced half was the wrong one. Newly ORDINARY rather than exotic: the FUNDS band's "+ Add a line" goes through `createCategory`, which does not write `target_cents`, where the only prior fund-creation path (`createGoalAction`) is `.positive()`. `GoalsView` also carries `totalTargetedContributedCents` and `untargetedGoalCount` so the headline ratio's two halves cover the SAME funds — the page summed contributions across every fund against a denominator of targets alone, which compares different sets and looks fine doing it.

2. **The CSV's signs are already correct.** `Amount Debit` is pre-negative, `Amount Credit` is positive, mutually exclusive. Parser rule: `debit ? debit*100 : credit*100`. No `Math.abs`, no negation by `Description`. The Plaid bug happens because Plaid transforms the data; this app doesn't.

3. **Dedup key is `(account_id, import_batch_id, import_row_hash)`**, never the bank's `Transaction Number`. Star One reuses `6098` as a pending-deposit placeholder across rows. `import_row_hash = sha1(date | amount_cents | raw_description | raw_memo | row_index_in_source_file)`.
   **`import_row_hash` alone is not enough on the CSV path either.** Star One exports an arbitrary date range, so re-exporting a wider window puts every already-imported row at a new offset and changes every hash — the hash pass then matches nothing and the whole overlap is inserted a second time while the preview reports "0 duplicates" (reproduced empirically, not theorized). `buildPreview` therefore runs a second pass on `contentSignature` (`src/lib/contentSignature.ts`, shared with sync), counted as a multiset so rule 3 does not regress. Rows already matched by hash claim their own ledger row's budget first, or an earlier identical row spends the budget of a row a later hash match already accounts for and a real second occurrence is dropped.
   A content match against an existing **pending** row is not just dropped: `commitImport` updates that row in place (`is_pending`, `balance_cents`, `bank_transaction_number`, `import_row_hash`) so a row CSV-imported while pending gets its posted counterpart merged in rather than silently absorbed by the dedup pass, which used to leave it stuck on Star One's `6098` placeholder forever — invisible to subscription detection, and (until v0.12.3) permanently un-pairable by the transfer matcher too, because `linkTransferPairs` re-checked rows by `importBatchId` and an updated-in-place row keeps its *original* batch's id, not the batch that posted it. `linkTransferPairs` now takes explicit seed row ids instead of a batch id, so `commitImport` passes both the newly-inserted rows and the just-posted `toUpdate` rows into the same re-check pass. Only a pending candidate is ever an update target, so a genuinely repeated posted duplicate (two identical same-day coffees) is untouched.
   **SimpleFIN rows dedup on `external_id` instead** — the feed's own per-account transaction id, enforced by a partial unique index on `(simplefin_source_account_id, external_id)`: unique within the FEED that issued it, which is what a SimpleFIN id actually guarantees (see the provenance paragraphs below for why `account_id` was the wrong scope). There is no row index in a JSON feed, so `import_row_hash` is derived from the external id. Because the feed re-sends days already imported from CSV, sync ALSO dedups on a content signature (`date|amount_cents|raw_memo`) counted as a multiset, so two genuinely identical same-day coffees still both survive. **The memo is whitespace-normalised (trim + collapse) on both sides of that comparison and nowhere else.** `parseCsv` preserves Star One's leading padding verbatim because `import_row_hash` depends on the exact bytes, while the feed sends the same row trimmed — so a raw string compare failed for precisely the rows this exists for (a row CSV-imported while pending, which later posts and comes back on the feed) and inserted them twice.
   **A sync row records WHICH FEED it came from, and that is a different fact from which account holds it.** `transactions.simplefin_source_account_id` (migration `0020`) is written at import time and never joined through `accounts` on read, because an account's link can be re-pointed and a row's origin cannot. The partial unique index is over `(simplefin_source_account_id, external_id)`, not `(account_id, external_id)`: a SimpleFIN id is unique within its own feed account, which is the thing the index is actually asserting — `account_id` was only ever a proxy for it, and a wrong one the moment a link moves.
   This replaced a fix that was itself the bug. `setAccountLink` used to CLEAR `external_id` off the account's rows on every relink, to dodge a collision on the old account-scoped index; clearing erased the only record of a row's origin, and since sync's content-dedup fallback is scoped to the account being synced (`eq(transactions.accountId, account.id)`), a *different* account claiming that feed next could not see the now-untagged rows at all and re-imported the whole overlap window, silently double-counting every amount. Nothing is cleared now, so a relink is a metadata-only change and the rows survive it intact.
   Three consequences worth knowing. The content-dedup fallback accepts rows tagged with a **different** feed, not just untagged CSV rows — re-running `pnpm simplefin:claim` mints fresh feed ids for the same real bank account, so the id pass genuinely cannot match, and the pre-fix clearing had been covering that case by accident. And `setAccountLink` warns about **two** things on a link change, joined into one string. (a) Rows on this account that no id pass can match, keyed on `simplefin_source_account_id IS NULL` and deliberately NOT on `external_id IS NULL` — a strict superset covering both **legacy orphans** (both columns NULL, stripped by a pre-`0020` relink) and rows that still CARRY an external_id but got no tag, which `0020` leaves behind for a sync row whose account was unlinked when it ran, since its backfill is `WHERE external_id IS NOT NULL`. Keying on the column that decides matchability is what keeps the second population from being invisible; an `external_id`-keyed query is structurally blind to it. The feed those rows came from is unknowable after the fact, which is precisely why the column has to be written rather than derived — that set can only ever shrink, and is empty on any ledger that never relinked before the fix. (b) Rows tagged with the feed being CLAIMED that are filed under a different local account. Sync will correctly refuse to re-import them — that is the dedup working — but they stay where they are, so the claiming account's balance is short by the whole overlap and rule 1's drift check reports phantom missing rows against it. That under-count is the accepted cost of recording provenance instead of moving rows (option (c) over (b) in the original decision), and the relink is the one moment a person can act on it, so it is reported rather than left to surface later as an unexplained gap.
   Third: **candidacy has to test `simplefin_source_account_id IS NULL` as its own case, and `ne()` is why.** `ne()` compiles to SQL `<>`, and `NULL <> 'ACT-1'` is NULL rather than true, so a row carrying an `external_id` with no provenance tag falls out of the OR entirely — invisible to the content pass, unmatched by the id pass (`= feedId` skips NULL), and unprotected by the partial unique index, since SQLite treats index NULLs as **distinct**. That row re-imports on every single sync. Migration `0020`'s backfill produces exactly it for a sync row whose account is currently unlinked, and its "a row still carrying an external_id has never been through a relink" argument does not cover that: `setAccountLink` only began clearing in v0.8.3 (`ca53e68`), five hours after sync shipped in v0.8.0 (`28aa181`), so a relink in that window left the tag intact. Measured 0 such rows before applying `0020`, and an unlink on `/sync` is one click — so it is defended in code (the third `or()` arm) rather than argued away. The general rule: **a three-valued `<>` is not the complement of `=`.** Any "everything except mine" predicate on a nullable column needs its `IS NULL` arm written out.
   The one boundary that is pinned rather than closed: a re-minted feed id wired to a **different** local account still re-imports, because content dedup is scoped `eq(accountId, account.id)`. Widening that across accounts is deliberately not done — two accounts can legitimately hold identical same-day rows — so `sync.test.ts` asserts the double-count instead of hiding it.
   **The id pass is RE-RUN inside the write transaction; the content pass deliberately is NOT (v0.26.0).** `seenExternalIds` is read in the staging loop, before the SimpleFIN round trip, and the insert happens after it — so a second sync (two `/sync` tabs, the same reachability bar rule 11's link guard is written for) can commit rows for the same feed in that window. The partial unique index catches them, so there is no double-count; the failure is what catching costs. A constraint violation aborts the ENTIRE transaction, taking with it good rows for accounts that were never in question, and surfaces the driver's raw `UNIQUE constraint failed` text — exactly the outcome the comment on `existingByContent` predicts. So `syncSimpleFin` re-queries `(simplefin_source_account_id, external_id)` against the handle that inserts, one query for the batch rather than one per row, and DROPS the rows another writer already landed. That is the correct reading of them — they are duplicates, and dedup is what the pass is for — and the count comes back as a warning, so a run that quietly shrank says so. The CONTENT pass is left in the staging loop on purpose: it has no unique index behind it, so a concurrent CSV `commitImport` in the same window produces a genuine duplicate ROW rather than an abort, which is quieter and worse. Widening the id query does not fix that, because the content budget is a multiset COUNT (above) and re-deriving it inside the transaction is a different and larger change than re-checking a unique key. It is a recorded residual in TODOS.md, not a closed one.

4. **Transfer pair matcher is MEMO-INDEPENDENT.** Two rows are a transfer pair iff: `|txn_a - txn_b| == 1` AND same date AND `|amount_a| == |amount_b|` AND opposite signs AND different accounts. Star One labels the receiving-side memo correctly only 20% of the time; the other 80% it mislabels with the triggering merchant. Memo is confirmation-only, never disqualifying. See `memory/project_star_one_cu_overdraft_labeling.md`.
   **This rule is CSV-only.** The SimpleFIN feed carries no transaction number and no `extra{}`, so `src/lib/simplefin/matchTransfers.ts` replaces it with a counting argument: bucket by `(date, |amount|)`, then within each bucket require opposite signs across different accounts, and when a bucket holds N positives and N negatives, every bijection excludes the same rows from spending — so link it without asking. Only unbalanced buckets need a human. Two refinements matter and are both load-bearing: ATM cash withdrawals are excluded from candidacy (they collide on the round amounts sweeps use), and counts are compared **per account-pair direction**, never globally (a charge in the same account as an inbound sweep is the purchase that triggered it, not a candidate for it). Cross-source pairs are held to a higher bar: when a leg carries a `bank_transaction_number` the CSV ±1 matcher already examined it and declined to pair it, so an uncorroborated pair with **either** leg adjudicated is sent to review rather than auto-linked — the counting argument must not override a stronger signal. That includes a CSV↔CSV pair where both legs were examined and declined, not just a mixed feed↔CSV one: both-declined is the *strongest* evidence against a real transfer, not the weakest, so the guard checks "at least one leg adjudicated," never an XOR between the two legs. Measured on real data: 56 pairs auto-link, ~1 undecidable day per 90. A third guard (refusing to guess when a bucket spans 3+ accounts) exists in the code but is inert here — only two accounts ever carry rows — so treat it as forward-looking, not load-bearing.
   **The CSV ±1 matcher's candidacy also excludes pending rows.** `linkTransferPairs`'s `sameDayUnpaired` query (`src/lib/importBatch.ts`) filters `is_pending = false`, mirroring rule 1's balance-sum filter: a still-pending row can carry Star One's shared `6098` placeholder transaction number (rule 3), which otherwise looks like a legitimate ±1 match for an unrelated posted row and would silently drop both from spending totals as a false pair. The *seed* query that triggers the same-day scan deliberately does **not** filter on `is_pending` — a pending row's own import still needs to trigger the scan (see below), it just can never be selected as a pair member itself; filtering both queries was tried and reverted because it made a pending-only import short-circuit before the date scan ever ran, silently losing the repair trigger below.
   **A manual "Not a transfer" correction is pair-scoped, not transaction-scoped, and it sticks.** `unlinkTransferPair` (`src/lib/simplefin/sync.ts`) stamps a nullable, self-referencing `transfer_rejected_partner_id` column (migration `0016`) on both legs, each pointed at the other — not just clearing `transfer_pair_id`, which used to leave a rejected pair indistinguishable from one that had simply never been evaluated. Without this, the same repair trigger that re-scans a shared date on unrelated activity (previous paragraph) could silently re-link the exact mismatch the user had just corrected, with no notification. A transaction-scoped flag (reject the row, not the pair) was tried first and reverted: it permanently blocked that row from ever pairing with its *real* counterpart too, and its only escape hatch, `linkTransferPairManually`, is reachable exclusively from `findAmbiguousTransfers`'s review queue — which the same flag would have hidden the row from. Both matchers take the rejection as an `isRejected(a, b)` predicate checked **before** committing a candidate, not as a post-filter over the result: `findTransferPairs` (`src/lib/transferPair.ts`) and `matchTransfers`'s bounded-backtracking `assignAvoidingRejections` (`src/lib/simplefin/matchTransfers.ts`) both keep searching for a different valid partner rather than dropping the whole bucket. `findAmbiguousTransfers` does not filter its own SELECT on the marker — a rejected row can still resurface there against a different candidate — but does pass `isRejected` into `matchTransfers` so a bucket whose only pairing was rejected still surfaces instead of vanishing. `linkTransferPairManually` clears the marker only when it currently points at the row actually being relinked, so relinking to a third row never erases an unrelated rejection.
   **A rejection is a ROW in `transfer_pair_rejections`, keyed on the unordered pair — not a column on either leg.** It was a single self-referencing `transactions.transfer_rejected_partner_id` through v0.19.0's development, documented as merely lossy ("a row remembers only its most recent rejection", estimated at four rejections across two rows to hit). The same-account reversal queue made writing a marker a ONE-CLICK act and turned that estimate into two distinct live bugs, so the store is now multi-valued:
   - **Erasure.** Rejecting `(A,C)` overwrote A's existing rejection of B. Two clicks in the reversal queue could clear both legs of an unrelated "Not a transfer", after which the automatic matcher re-linked the exact pair the user rejected — silently dropping both rows out of every spend total.
   - **Non-convergence.** `findSameAccountReversals` drops a bucket only once EVERY positive/negative combination is rejected. P·N combinations competed for P+N column slots, so for P≥2 **and** N≥2 the all-rejected state was *unreachable* — proved by exhaustive search over the reachable states, and live on the real ledger as a 2×4 bucket where 3 of 8 combinations stayed live whatever the click order. The queue could not be dismissed and claimed "won't be suggested again" every time.

   Two consequences worth knowing. `linkTransferPairManually` no longer needs its conditional "clear the marker only if it points at the leg being linked" — one row per pair means there is nothing to clobber. And `assignAvoidingRejections`' complexity argument is gone: it relied on out-degree ≤ 1 per row to keep backtracking near-linear, so the search is now explicitly budgeted (`SEARCH_BUDGET`), failing over to "send the bucket to review" rather than exploring a dense rejection graph on a synchronous driver.
   **"Different accounts" is still true of every AUTOMATIC matcher — and as of v0.19.0 there is one human-only exception: a SAME-ACCOUNT reversal.** A transaction and its cancellation can both land on one account (a reversed `A2AXFER`, a disputed charge and its provisional credit, a returned payment). `findTransferPairs`, `matchTransfers` and `linkTransferPairManually` all refuse a same-account pair, so nothing could see that class and there was no way to pair it by hand either; it stayed filed as spending forever. `findSameAccountReversals` (`src/lib/simplefin/sameAccountReversals.ts`) finds it by bucketing on `(accountId, date, |amount|)` — one key tighter than `matchTransfers`, because here the account defines the class rather than being the thing compared across.
   **It NEVER auto-links, and that is the whole design, not a phase-one limitation.** The shape alone (same account, same day, equal magnitude, opposite signs) is not evidence: measured across the live ledger's 8 months, 15 candidates of which at least 2 are coincidences — a $3.99 ATM-fee refund opposite a real $3.99 Apple charge, a $200 Zelle receipt opposite a genuine $200 ATM withdrawal. Auto-linking either would silently delete real spending from every spend surface. A genuine merchandise refund fits the shape too and should NOT be paired, because under the signed-spend convention it already nets correctly and stays visible. The distinguishing signal lives in memo text (`reverse`, `Reversal ID:`, `Provisional Credit`, `TO`/`FRM`), and memo-independence is this rule's deliberate property — so the function returns `AmbiguousBucket[]` and nothing else, and every candidate goes to the `/sync` review queue. At roughly two a month a person classifies these instantly.
   **The same-account opt-in is a server-action ARGUMENT, never a form field.** `linkTransferPairManually(aId, bId, db, { allowSameAccountReversal: true })` is passed only by the same-account queue's own action; a crafted or stale form post cannot set it. Inside the opt-in, two further checks narrow it: the legs must be same-day (otherwise it would accept any two opposite-sign rows of equal size anywhere in one account's history — a shape no reviewer is ever shown), and a `manual` row is refused outright (pairing a hand-entered row hides it from every spend surface and `unmarkCardPayment` refuses a pair it did not create — precisely: it classifies a leg as its own synthetic mirror via `importSource === 'manual' && categoryId === null`, so a *categorized* hand-entered row hits the refusal while an uncategorized one would be DELETED, which is worse. Either way there is no ordinary way back).
   **The one field that IS on that form — `intent` — is REQUIRED, with no default (v0.22.0).** The reversal card carries two submitters with opposite effects on money: link (pairs the rows, removes both from every spend surface, and CLEARS any `transfer_pair_rejections` row for the pair) and reject. `intent` used to be `.default("link")`, documented as the fail-safe direction because link "has the stricter guards and is the reversible one". Both halves were false: every guard `linkTransferPairManually` applies to such a pair is satisfied BY CONSTRUCTION for anything this queue can render, so none of them can tell a dropped field from a deliberate click, and `clearPairRejection` makes the link destructive of a decision the user already recorded rather than undoable. Only TWO of those guards actually live inside the `allowSameAccountReversal` opt-in — same-day and not-`manual`, both inside the `a.accountId === b.accountId` block. Opposite signs, equal magnitude and neither-leg-already-paired sit OUTSIDE it and apply to every pairing unconditionally; `resolveSameAccountReversalAction`'s docblock draws the same line, and it matters because a cross-account pair posted to that action is date-unchecked exactly as it is on the ordinary transfer action. The real defect was that ABSENCE was the affirmative signal for the destructive branch — "the user pressed Link" and "the submitter's field was lost" were identical on the wire. Both buttons now name themselves (`LINK_INTENT`/`REJECT_INTENT` in `src/lib/simplefin/validateSyncInputs.ts`, imported by `_review-queue.tsx`; `actions.ts` imports `REJECT_INTENT` alone, since `LINK_INTENT` reaches the action as the `else`), so a lost submitter is a refusal. Do not restore a default on a discriminant whose branches disagree about money — and note that `tsc` cannot stop you: `z.infer` is byte-identical with and without `.default("link")`, because a default changes only the INPUT type. That is why `_INTENT_IS_REQUIRED` (a `z.input`-based compile-time assertion, the same idiom as `_filter-bar.test.ts`'s `NO_UNCARRIED_SCHEMA_KEYS`) sits beside the schema: without it the invariant this whole change is about was defended by two runtime tests and nothing else. The field NAME is duplicated in `src/app/sync/_submit-button.tsx` — a client component, which cannot import the zod module's VALUES without pulling zod into the /sync bundle (the +376 KB `limits.ts` case) — but a `import type` is erased, so that literal is pinned with `satisfies keyof ResolveReversalInput` and a rename is a build error there too. REQUIRED-ness remains the runtime backstop that makes drift fail loudly for BOTH buttons on the first click instead of silently taking one branch; it is the same protection as `_INTENT_IS_REQUIRED`, not a second independent one.
   **The link REPORTS the rejection it erased.** `clearPairRejection` returns whether a row was actually deleted and `linkTransferPairManually` passes it out as `{ clearedRejection }`; both returned `void` until v0.22.0, so the one surface that performs the erasure could not have mentioned it. This is not cosmetic: on a multi-candidate bucket a rejection leaves `bucketKey` unchanged and both `<select>`s still showing the pair just rejected, so the card is byte-identical afterwards and the next click on "Link as reversal" silently reverses an answer the user believes is still recorded. There is no surface anywhere in the app to get that row back. Note `clearPairRejection` reads before it deletes rather than using `.run()`'s `changes` — `AnyDb` erases the driver result type, the same constraint `recordPairRejection` documents two functions above.
   **`rejectTransferPairManually` records "not a pair" WITHOUT linking first.** `unlinkTransferPair` writes the same `transfer_pair_rejections` row but only for an already-linked pair, so the only route to a durable rejection used to be to create the link you were rejecting and then undo it — and between those two clicks both rows leave every spending surface, and on a card the positive leg briefly counted as debt paid down. It refuses a pair either leg of which is already linked (that is `unlinkTransferPair`'s job). Rejection stays pair-scoped: `findSameAccountReversals` drops a bucket only once EVERY positive/negative combination in it is rejected, so a one-vs-one refund is answered once and never nags again while a multi-candidate bucket keeps surfacing its live combinations.
   **The two review queues can legitimately claim the same row, and both show it.** `matchTransfers`' same-account exclusion is a per-BUCKET test (`accountIds.length < 2`), so a `(date, |amount|)` holding a same-account +/− pair AND rows on another account passes it — measured 2026-09-08 as 1 of 14 buckets. That overlap is a real ambiguity (a reversal on A, or the blessed bidirectional A→B / B→A pair `matchTransfers` already auto-links), not a bucketing bug; stripping same-account rows before the counting argument was tried and reverted because it killed two real auto-links. `overlappingRowIds` computes the shared ids and `/sync` labels them in both queues. **PAIRING it once removes it from both; rejecting it does not** — a rejection is scoped to the pair it names, so "Not a reversal" leaves the cross-account reading standing. The UI copy says pairing for that reason.

5. **Every batch import writes a DB snapshot first**, to `data/money.db.pre-import-{timestamp}`, before any write. Rollback = stop dev server, swap file. Sync does this too, and additionally supports a logical undo (delete the batch's rows) that works without stopping the server — the file snapshot stays as the escape hatch. That undo is only offered while the sync batch is still the newest `import_batches` row of any source: CSV content-dedup has no source filter, so a later CSV import can content-match against a row the sync batch inserted and skip it, quietly relying on that row already being there. `undoSyncBatch` re-checks the same condition inside its own transaction (a second tab, a stale form resubmit) rather than trusting the page's initial check.
   Snapshots are written with `VACUUM INTO`, not a file copy. The DB runs in WAL mode, and `PRAGMA wal_checkpoint` does **not** throw when another connection holds a read — it reports `busy` in a return value. Measured: with a reader pinned, a checkpoint-then-copy produced a file that failed to open at all (`SQLITE_CORRUPT`). `createSnapshot` reports `consistent: false` when it has to fall back to a plain copy; do not silently ignore that flag. Both `commitImport` (CSV) and `/sync` check it; when it's false, a warning is persisted on `import_batches.snapshot_warning` (not a redirect query param — it has to survive a later visit to the batch's success page, not just the one right after commit) and rendered on `/import/success/[batchId]`. The import itself still proceeds — a degraded snapshot changes the safety net, not whether the write happens.
   `snapshot_warning` is a general per-batch warning channel despite the name: `anchorStartingBalance` (rule 1) also joins its own decline reasons onto the same column, and as of v0.26.0 so does sync's link re-check (rule 11) — the sentences naming an account whose rows were withheld mid-run lived only in one `useActionState` value, so closing the tab left dozens of unimported bank rows with no record anywhere, which is at least as consequential as a degraded snapshot and settled by the same argument this paragraph already makes. So a non-null value does not by itself mean *this batch's snapshot* is degraded — check `snapshot.consistent` from the commit result for that specifically.
   **A sync that writes nothing mints no batch and keeps no snapshot.** When the link re-check withholds every staged account, `syncSimpleFin` throws `NothingVerifiedError` purely to roll its own transaction back, `unlinkSync`s the snapshot it had already taken, re-derives the warning sentences outside the discarded transaction (`verifyStagedLinksReadOnly` — sound precisely because nothing was written, so there is no ordering guarantee left to protect, only copy to rebuild), and returns the same `up-to-date` shape a quiet sync uses. Committing instead left an empty `import_batches` row, and an empty batch is not inert: `findLastSyncBatch` returns the NEWEST sync batch, so it became the undo target and the previous real sync's undo silently became unreachable — the rollback for the last import that actually wrote anything, gone, with nothing saying so. It also spent one of the ten retention slots on a snapshot of a ledger the sync did not change, which is the harm the prune-after-commit ordering below exists to prevent, reached through a door that ordering does not cover.
   Retention (last 10) is `pruneSnapshots`, called by the caller **after** its write commits — never inside `createSnapshot`. Pruning before the write meant a failed import had already evicted a real snapshot to make room for a useless one.

6. **Uncategorized transactions have `category_id = NULL`** and surface in the dashboard backlog tile. The "Uncategorized" seed category is for manual overrides; NULL is the default for unmatched rows.
   Both write paths auto-categorize on the way in: `commitImport` and `syncSimpleFin` resolve each row's `normalized_merchant` through `buildRuleMatcher` (`src/lib/rules.ts`, which reads and ranks the rules table once per batch rather than once per row). `applyRuleAtImport` was written, tested and documented as doing this in v0.3.0 and had **zero production callers** until 2026-09-02 — every import landed 100% uncategorized regardless of trained rules, which is how a 498-row backlog accumulated. Import-time categorization now has its own undo: both write paths record an `import_batch_categorizations` row (transaction id, category id, rule id) whenever a rule matches, and `undoImportCategorization` (`src/lib/categorize/`) reverts a batch's rule-matched rows — grouped per category, stale-row-safe (a row the user re-categorized since is left alone) — from a button on `/import/success/[batchId]`. Unlike `bulkCategorize`'s undo, there is no rule to roll back: import-time categorization only applies an existing rule, never creates or edits one.
   **Not every `normalized_merchant` may back a rule (v0.20.0).** "Remember" used to upsert an `exact` rule from whatever key the row carried; from then on `buildRuleMatcher` files every future match without asking again, so a rule trained on a bad key is silent forever. `classifyKeyTrainability` (`src/lib/categorize/keyTrainability.ts`) refuses two classes, derived differently ON PURPOSE. **Lossy** keys — `ONLINE`, `MOBILE`, `""` — are a CURATED set (`LOSSY_MERCHANT_KEYS`), because the text that named a counterparty is already gone by the time the key exists; the bar is live rows OR a demonstrably reachable output that by construction names nobody, which is the only reason `""` (zero rows today) qualifies. Measured across ALL rows for the key, not the uncategorized backlog: `ONLINE` 39, `MOBILE` 27, spanning a prescription, a Taco Bell reimbursement and a refinance. `KNOWN_CITIES` is the comparable evidence-derived list in `normalize.ts` — `STATE_CODES` is NOT one, despite an earlier version of this note; it is the complete US list and is justified on being strictly narrower than the regex it replaced. **Multi-category** keys are READ FROM THE DATA, no list to maintain.
   The verdict needs the UNION of the key's already-filed category ids AND the category being assigned right now — the pick in flight is what turns a unanimous merchant into a split one, and that is the case that most needs the warning. But the two are SEPARATE parameters (`classifyKeyTrainability(key, filed, pending)`), because the MESSAGE must not be built from the union: reporting its cardinality as history said "already filed under 2 different categories" about a merchant filed under exactly one, which is the user's only explanation for a disabled checkbox and for a rule that just got removed. The function also decides what counts as a real id, so neither caller has to: `Number('')` is `0` and `Number(<corrupt sessionStorage pick>)` is `NaN`, and both used to read as a phantom second category.
   **Order-independence is by construction, not by discipline.** `resolveKeyTrainability` takes `excludeTxnIds` — the already-filed rows the caller is about to retarget — so the verdict describes the ledger AS IT WILL BE and is the same read on either side of the caller's own UPDATE. This replaced a "MUST be called before your own UPDATE" comment repeated in three places, and it fixed a real refusal: moving a key's ONLY filed row to a new category used to be refused on the category the row was leaving, which does not exist for that key once the action commits. `bulkCategorize` passes nothing (it only touches `categoryId IS NULL` rows, which the filed query already skips); `categorizeTransaction` passes its target id; `bulkRetarget` (v0.23.0) passes the WHOLE moved set, and that is the caller the parameter matters most for — the rows it is moving are exactly the evidence that made the key look multi-category, so without the exclusion the guard would refuse to retrain a key this very call is about to make unanimous.
   **A refusal MAY also delete the exact rule the key already had, and every condition on that is load-bearing.** `applyRuleWrite` (`src/lib/categorize/applyRuleWrite.ts`) is the ONE place that decides; `deleteExactRule` and `readExactRule` (`src/lib/rules.ts`) decide nothing. Withholding the write alone was not enough: a wrong rule keeps auto-filing every future import, which leaves the merchant no NULL-category rows and so keeps it off `/categorize`, and the only other retrain path — ticking Remember on a `/transactions` row — is exactly what the guard refuses, because the rows that rule filed are what make the key look split. There is no rules-management surface, so the rule would have been permanent. Three conditions narrow it:
   - **`allowRuleRemoval` is an ARGUMENT, defaulting to FALSE** — the same discipline rule 4 applies to `allowSameAccountReversal`, and for the same reason: it must not be reachable from a form. Only the two deliberate per-merchant retrains opt in (`/categorize`'s and `/transactions`' actions). `/subscriptions` does not, and that is the point — "Categorize all" loops every active detection with `rememberMerchant: true` and no per-merchant intent, and `loadSubscriptions` does not filter on `category_id`, so a merchant already filed under a correct rule is still on that list. One click could delete a rule per such merchant, unrecoverably: that page has no undo.
   - **A MULTI-CATEGORY refusal deletes only when the user CONTRADICTED the rule's target** (`existing.categoryId !== categoryId`). Picking the category a rule already points at is confirming it, and deleting it there left every future row for the key uncategorized for nothing.
   - **A LOSSY refusal always deletes**, because a lossy key cannot back a correct rule pointing anywhere at all.

   What it deliberately does NOT do is spare a rule a lot of history agrees with: retarget one of 50 rows filed by `K → Shopping` and the rule goes. That is the same shape as the case the deletion exists for and the difference is intent, which is not in the data — so it takes the better of two wrongs. Afterwards new `K` rows land uncategorized and surface on `/categorize`; keeping the rule means they are silently filed where the user just said is not the only answer, and rule 6's thesis is that the silent version is the worse one. The cost is paid at the surfaces instead: the notice NAMES the removed rule's category (`describeRuleRefusal`, `src/lib/categorize/refusalNotice.ts`) and its Undo is on the FRONT toast. The deleted row is snapshotted into `priorRule` and both undo paths go through `restorePriorRule`. Note this cuts against rule 10's assumption that a rule can always be retrained from a row.
   **As of v0.23.0 the user has an action that reaches the other 49.** `bulkRetarget` moves every row filed under one category for a key in one step, and passes the whole moved set as `excludeTxnIds` — so ticking Remember on a move that MAKES the key unanimous retrains the rule instead of removing it. The single-row case above is unchanged and still removes the rule: one row does not make a key unanimous, and intent is still not in the data. What changed is that the repair is now a two-step a person can actually complete (move the history, then let the rule follow it) rather than 50 individual re-files after a 10-second undo expired.
   **`restorePriorRule` has three mechanisms, and the third exists because uniqueness is on `(match_type, match_value)`, not `id`.** UPDATE by id, else INSERT under the same id, else — when something now occupies that slot — `onConflictDoUpdate` onto the occupying row. A plain INSERT threw `UNIQUE constraint failed` there, and since both undo paths call this inside their transaction AFTER reverting rows, the throw rolled the whole undo back and surfaced a raw SQLite error. Reachable in ordinary use: a refusal removes the rule, a second Remember tick trains a new one, the first action's 10s Undo is still open. It restores `created_at`/`updated_at` too — `compareRules` breaks priority ties on `updated_at DESC`, and rule 10's backfill DELETES the loser of a collision by that order. One thing it cannot recover: `import_batch_categorizations.rule_id` is `onDelete: 'set null'`, so the delete nulls provenance on every row that rule filed and the re-insert does not restore it. No reader exists today.
   **A single toast, never a success plus a warning.** `<Toaster>` runs Sonner's default collapsed stack (`expand` unset), where `[data-front="false"] > *` is `opacity: 0` — so a non-newest toast has its ACTION BUTTON drawn invisible until the stack is hovered. Two toasts therefore forced a choice between the warning being readable and the Undo being reachable, and that Undo is the only way back inside 10 seconds. Ordering them was tried in both directions; merging them is the fix.
   **Refusal withholds the RULE ONLY — the rows are still categorized.** The user's decision about those rows is sound even when generalizing it is not. That includes the `""` key: it is lossy, so Remember is refused, but its rows file like any other group's. `""` is a real stored key at all THREE validation boundaries now (`validateBulkCategorizeInput` plus both snapshot schemas) — a `.min(1)` on any one of them broke either filing or undoing the one group with no other repair path.
   **`/subscriptions` cannot REMOVE a rule but CAN retarget one, and both halves have to be said.** Not passing `allowRuleRemoval` closes the destructive half; it does not close the upsert, which repoints an existing exact rule's category on a trainable verdict. That is reachable with no crafted input: undoing a batch's import-time categorization resets its rows to NULL and deliberately leaves the rule standing, so the key reads as UNFILED, the verdict is trainable, and one click on a detected subscription repoints a hand-trained rule — with no undo anywhere on that page. So `fileSubscription` reports `retargetedRule` with the same weight as a refusal. The same shape reaches it through an archived category, whose rules never fire (rule 8) and whose filings the evidence predicate now skips.
   **All three `bulkCategorize` callers read the result.** `src/app/subscriptions/actions.ts` used to discard it, which made refusals and rule deletions invisible on the one surface that loops. Its notices are the SERVER's own per-merchant sentences, never a summary composed in the client: generalizing over them reintroduced the exact false claim ("filed under more than one category") that splitting the message from the union was meant to eliminate, and it is false for the commonest case on that page. Its logic now lives in `src/lib/subscriptions/categorizeSubscriptions.ts` (explicit `db`, therefore testable) and reports per-merchant outcomes; `_categorize-buttons.tsx` renders them through Sonner like the other two surfaces. The sweep collects a per-merchant throw into `failures` rather than propagating — each merchant commits in its own transaction, so propagating abandoned every later merchant AND left no record of how far it got, while one big transaction would discard every good filing over one bad merchant.

7. **Migrations that rebuild a table run through `scripts/migrate.mjs`, never `drizzle-kit migrate` directly.** SQLite only relaxes a `NOT NULL` column via a table rebuild (drop + recreate), and drizzle's migrator wraps every pending migration in a single `BEGIN`/`COMMIT`. `PRAGMA foreign_keys=OFF` inside the migration SQL is a documented no-op there (SQLite only honors it outside a transaction), and `defer_foreign_keys=ON` doesn't help either — SQLite's deferred-FK bookkeeping is a violation *counter*, not a final-state check, so `DROP TABLE` on an FK-referenced table (`import_batches`, in the migration that introduced this) fails the moment real rows reference it, even though the rebuilt table ends up satisfying every reference by commit. An empty dev database never hits this path. `scripts/migrate.mjs` disables `foreign_keys` on the connection *before* calling `migrate()`, so it's already off when the migrator's own `BEGIN` opens, then runs `PRAGMA foreign_key_check` afterward as a belt-and-suspenders integrity check — that pragma works regardless of the `foreign_keys` setting, so there's nothing to restore on a connection that's about to close. A rebuild is written with a `VACUUM INTO` snapshot first (same approach as rule 5, `data/money.db.pre-migrate-{ts}`), skipped only when there's no existing database yet. `pnpm db:migrate` runs this script; don't bypass it. `scripts/db-paths.mjs` exports `dbPath()` (reads `DATA_DIR` at call time, mirroring `src/lib/paths.ts`'s `dataDir()` — duplicated rather than imported, since both consumers run as plain `node`/`drizzle-kit` processes with no TS loader) and `MIGRATIONS_FOLDER`, imported by both this script and `drizzle.config.ts` so the two can't disagree about where the ledger lives. Before this, `db-paths.mjs` hardcoded a cwd-relative path and ignored `DATA_DIR`, so running `pnpm db:migrate` from the wrong working directory could silently migrate an unrelated, empty database and report success.

8. **A category's `kind` (`'income'|'expense'|'fund'`) is fixed once the category is "used"** — at least one transaction or `budget_periods` row. **A FUND can acquire that `budget_periods` row as of v0.23.0**, when the `/budget` FUNDS band became editable; before that a fund had no write path to one, so `isUsed` was effectively transactions-only for `kind='fund'`. That made a `$0` allocation — or one "Copy previous month" — lock a fund's kind forever while the row's own `CategoryMenu` went on offering to change it, a refusal the user could only discover by triggering it. **`src/lib/budget/categoryKindLock.ts` is the ONE spelling of this rule as of v0.24.0**: `isCategoryUsed` + `assignableKinds` (pure) over `loadCategoryKindUsage` (the drizzle half), read by BOTH the writer that enforces it (`setCategoryKind`) and the read model that has to render an honest menu (`loadMonthView`, which ships `assignableKinds` on every row type). They are not allowed to derive it independently — that divergence is what the defect was. One thing the shared spelling cannot cover: the menu's prop is server-rendered and `commitAllocationAction` deliberately does not revalidate, so `liveAssignableKinds` (`_month-editor.tsx`) closes the window between an allocation commit and the island losing focus. Its guard — `kindsImplyUsed(serverKinds)`, the `< 3` test named below — is load-bearing and counter-intuitive — it deliberately does NOT narrow the two-entry X1 case, because blanket-narrowing on a live allocation would withdraw the one repair path X1 exists to provide. The one exception (X1): expense → income is allowed on a used category whose transactions are *all positive* — the repair path for a category that was always income but got named/seeded like an expense, since `leftToBudgetCents` is uncomputable with zero income categories. Every other kind transition on a used category is refused outright, with the transaction count and date range as evidence rather than a bare rejection. `archived_at` (nullable timestamp) excludes a category from every picker and stops its auto-categorization rules (`buildRuleMatcher` skips an archived category's rules) — but never deletes it, and it is NOT unconditionally hidden from `loadMonthView`: `notHiddenByArchive` (`src/lib/budget/loadMonthView.ts`) only hides an archived category from a month where it has neither a nonzero allocation nor any spend that month, so a month it already has activity in (including the current one) keeps showing it — archiving can never erase a month's numbers. `/budget/categories` is the one surface that still lists (and can unarchive) it. `archiveCategory` refuses the built-in `Uncategorized` category, any category with children (parents are header-only), and any category with a nonzero *allocation* (not spend — only `budget_periods`, not transactions) in the current or a future month.
   **X1 additionally REQUIRES a `confirmedIrreversible` argument, and absence is a refusal (v0.26.0).** `setCategoryKind(db, id, kind, { confirmedIrreversible })` throws `UnconfirmedIrreversibleKindChangeError` when the transition it is about to take is the X1 one and the caller did not pass it. It is ignored on every other permitted transition, because those are all on an unused category and freely reversible — a modal there is friction that teaches people to click through modals. The client gate was not enough by itself and structurally could not be: `CategoryMenu` decides whether to confirm from a SERVER-RENDERED prop, and `commitAllocationAction` deliberately does not revalidate, so the prop is stale by design. Concretely, a tab that rendered a category as unused while "Copy previous month" created a `budget_periods` row in another tab offered the one-way change with no dialog, no ellipsis and no destructive styling — and X1 accepted it, because `negativeTxnCount === 0` is vacuously true at zero rows. So the confirmation is a fact the SERVER checks, not one the client is trusted to have performed. This is the same discipline rule 4 arrived at for the reversal form's `intent` after the mirror-image bug: **never let ABSENCE be the affirmative signal for the irreversible branch.** The threat model is a stale tab, not a crafted post — the app is single-user, local and unauthenticated, so a hand-built form could always set the flag; what it cannot do is set it by accident, which is the entire population of real occurrences. `setCategoryKindAction` takes it as `z.literal("yes").optional()` and `CategoryMenu` deliberately does NOT send it on the reversible path, since a flag that is always present means nothing.
   **And it took X1's OTHER caller out for a whole release (v0.27.0).** X1 has exactly two entry points — `CategoryMenu`'s kind item and `ReclassifyIncomeBanner` (`_reclassify-income.tsx`) — and v0.26.0 updated only the menu, so from the moment the argument landed the banner was refused on every candidate it could list — with no residual population it still worked for, because `loadReclassifyCandidates` requires `count > 0` transactions, which is precisely "used". Not a corner: the banner is the ONLY repair for an uncomputable `leftToBudgetCents`, which is rule 8's own justification for granting the exception at all. Nothing caught it. `tsc` cannot — the flag rides in an options bag with a `= false` default, so an omitting caller type-checks — and `setCategoryKind`'s tests pass the flag DIRECTLY, so the writer was covered and the caller was not. **When a shared writer grows a defaulted-false required argument, enumerate its callers; the omission is a runtime refusal, not a compile error.** The banner sends it honestly rather than as a rubber stamp: that dialog IS the confirmation the server is asking about — it names the consequence, requires an explicit pick, and disables the button until the picked category is all-positive. What neither caller may do is send it from a path with no dialog.
   **The `< 3` reading has a name now, in a DB-free module.** `kindsImplyUsed(kinds)` + `ALL_KINDS` (`src/lib/budget/kindsImplyUsed.ts`) is the one spelling of "this kind list came from a used category, so the only change on offer is X1, so it cannot be undone" — exact rather than heuristic, since `assignableKinds` returns all three kinds if and only if `!isCategoryUsed`. The literal had grown THREE inline copies (`_month-editor`'s `liveAssignableKinds` and `liveKindLockReason`, plus `CategoryMenu`'s confirm gate), and the newest of them decided whether an irreversible write got a confirmation step — a rule 8 fact restated in a component where no test could reach it. It is its own file rather than a function in `categoryKindLock.ts`, and that module deliberately does not re-export it: `categoryKindLock.ts` imports `drizzle-orm` and `@/db`, both callers are `"use client"`, and a value import would pull better-sqlite3 into the browser bundle — the measured +376 KB `limits.ts` shape, reintroduced by the very bridge meant to keep rule 8's vocabulary in one place. `ALL_KINDS` exists because the `3` was the CARDINALITY of the schema enum with nothing tying it there: add a fourth kind and `kindsImplyUsed` starts returning `true` for an UNUSED category, so the confirm dialog fires before a reversible change and trains people to click through the one modal in the app that guards a one-way write, with `tsc` silent throughout.

9. **A liability's balance is stored NEGATIVE, and the user never types a minus sign.** Owing $2,000 on a Visa is `starting_balance_cents = -200000`. Every consumer already handled a negative balance (an overdrawn checking account), so the sign convention needed no new branch downstream — that is the whole argument for it. The form says "Balance owed" and takes a positive figure; exactly one function negates it, `owedDollarsToSignedCents` (`src/lib/import/accountAnchorFields.ts`), shared by account creation and by `/accounts`' Reconcile. Those two used to negate independently and disagreed: one computed `-Math.round(owed * 100)` and the other `Math.round(-owed * 100)`, which differ by a cent on any half-cent input because `Math.round` breaks half-values toward +Infinity. Round first, flip the sign second, in one place. Getting this wrong is silent and expensive — a positive anchor on a card adds the debt to the dashboard's Cash figure and leaves net worth wrong by twice the balance, with a number that looks entirely plausible.
   `accountClass(type)` (`'asset'|'liability'`) is DERIVED from `accounts.type`, never stored, and `isLongTermLiability(type)` is the single switch behind the mortgage-vs-card divergences it actually owns: the muted money weight, the `LONG-TERM` grouping, the card-only affordances (no hand-entered charges, no card-terms form), and the feed sign guard — a positive balance from SimpleFIN is REFUSED on a loan, which can never legitimately hold one, and written-with-a-warning on a card, which can after an overpayment (`summarizeBalances` treats that as real, so `liability ⇒ negative` is a convention, not an invariant). Do not add a second independent derivation of "is this a mortgage."
   **It does NOT gate the balance control, and it does NOT gate the utilization bar.** Both were tried that way and both were wrong, so the doc names the real mechanism instead:
   - The balance control is chosen by `resolveBalanceAction(account, hasAnyRows)` ALONE — feed-linked with zero rows offers Refresh, everything else offers Reconcile. **A mortgage does get Reconcile.** ANDing `!longTerm` into that choice left an unlinked car loan rendering *neither* control, with its balance unreachable: `manualTransaction` refuses a loan (E17) and `/import`'s repair form excludes every liability (E18) while pointing the user at this page. See the comment at `src/app/accounts/_account-row.tsx`'s DS55 block, and commit `b1c3ab9`.
     **And the converse held too, until v0.27.0: `resolveBalanceAction` must not gate the CHARGE affordance.** `CardControls` was MOUNTED only on the `reconcile` branch, which silently made two things that have nothing to do with the balance control — "Add a charge" and the card-terms form — conditional on it. A feed-linked card with no rows resolves to `refresh`, so it rendered Refresh and nothing else: the card could not receive its first hand-entered charge (you needed a row to reach the form that creates a row) and a mistyped `credit_limit_cents` could not be repaired, which is the one job that form exists for. `showReconcile` now relays the answer instead of deciding what else mounts. DS55's own comment had said the charge affordance was "a genuinely separate question" all along; only the nesting disagreed.
     **Un-nesting it then produced THREE gates where there had been one, and collapsing any two of them back together is a regression each way.** `showReconcile` is the balance control. `canAddCharge` is `!longTerm && chargeableDateExists`, where `chargeableDateExists` is `startingBalanceDate < today`: `createCardActivity` refuses `date <= startingBalanceDate` and the dialog caps the date at today, so on a card whose anchor IS today the legal date set is EMPTY and the button could only ever refuse — and `refreshLiabilityBalances` writes that anchor from the bank's own balance-date, so that is the ordinary state on a sync day rather than an edge case. Hiding it there is rule 8's pattern applied outside rule 8: v0.24.0's `assignableKinds` established that a refusal the user can only discover by triggering it is worse than an absent control. `canEditTerms` is `!longTerm` and NOTHING else, because terms have no date to refuse — riding them on the charge gate made `Card details` vanish on a card anchored today, taking the credit-limit repair with it, which is the exact half of the deadlock the un-nesting existed to fix. And `CardControls` now returns null when all three are false, because un-nesting also means it is mounted on a feed-linked mortgage that has nothing at all to draw.
   - The `/transactions` row menu offers "Remove this charge" for `import_source='manual'` rows and nothing else, which is what makes the first row on a card REVERSIBLE — delete the last one and both `resolveBalanceAction` and `refreshLiabilityBalances` pick the account up again, because they ask the same question of the same table.
   - The utilization bar is gated on `credit_limit_cents` being present, because DS64 makes the limit optional. Deriving it from type instead filed an ordinary card the user hadn't entered a limit for under `LONG-TERM`, muted and stripped of Reconcile (E7). Two independent derivations, neither standing in for the other.
   **`/accounts` is the ONLY anchor surface for a liability.** `/import`'s repair form is the raw *signed* twin of Reconcile — it takes a signed balance with no relabelling and no negation — so it filters to assets and rejects a liability `accountId` server-side (E18). CSV import does the same (E6). A liability reaching either path reintroduces the corruption the sign convention exists to prevent.
   **`credit_limit_cents`, `minimum_payment_cents` are cards-only** (`type='credit'`), enforced server-side rather than by where the form renders — a mortgage row draws neither, so storing them there persists a figure nothing reads. A NULL credit limit means "no limit recorded" and is NOT the same fact as `0`; `""` from an emptied number input must clear to NULL, never coerce to zero (`optionalPositiveDollarsSchema`, shared by the create and repair paths).
   **"Paid down this month" (`paidDownCents`) counts positive card rows that are paired ACROSS accounts — "paired" alone is not enough.** E13 already required a pair (an unpaired positive on a card is a merchant refund, not a payment), and the reasoning behind it was that the only way a card's positive row could be paired was the checking-side withdrawal that paid it. Same-account reversals (rule 4) broke that inference: a disputed charge's provisional credit, paired with the charge it cancels, satisfies `transfer_pair_id IS NOT NULL` on the positive leg. Measured during /ship 2026-09-08 taking the figure from $0.00 to $200.00 on `/accounts` and the dashboard for money that never left checking. The query now carries an `EXISTS` on the partner row's `account_id <> ` the row's own, which restores E13's intent rather than narrowing it — a real payment is cross-account by construction.
   **`prior_starting_balance_cents`/`_date` hold exactly ONE prior anchor, not a series.** Every liability path that moves an anchor records it — Reconcile and the sync balance pass — which is what makes `revertLiabilityBalanceAction` possible. Because there is exactly one slot, WHERE the prior value is read from is load-bearing rather than incidental: the sync balance pass reads it inside its own per-account transaction, off the row as it stands at write time, never off the account loaded before the feed round trip (rule 1, rule 11). A hand Reconcile landing in those seconds was otherwise overwritten AND had this slot filled with the figure it had just replaced — one undo, spent on a value that was never current, while the run reported "up to date". It SWAPS rather than clears, so the undo is itself undoable; the cost is that it is a toggle rather than an idempotent operation. The asset-only `/import` repair path deliberately does NOT write these columns, because nothing can read them for an asset. A debt trend line needs a real history table and is unbuildable until one exists.

10. **`normalized_merchant` is derived ONCE, at write time — so changing `normalizeMerchant` desynchronizes the ledger from the code until `pnpm db:backfill-merchants` runs.** The column is written by the three write paths (`commitImport`, `syncSimpleFin`, `manualTransaction`) and never recomputed on read. Change the normalizer alone and every stored key belongs to the previous generation, which is worse than it sounds and entirely silent:
    - `buildRuleMatcher` matches an `exact` rule with `===`, so every trained rule still holding an old key stops firing on newly imported rows. Measured on the real ledger when this was first attempted: auto-categorization fell from **672 rows to 196**.
    - `/categorize` groups on the STORED column and `bulkCategorize` copies that value straight into a new rule, so rules trained during the gap are **born unable to match anything**, with the UI reporting success.
    - `detectSubscriptions` has no staleness filter, so an abandoned key keeps its history and consistent intervals forever: one real subscription shows as a frozen phantom plus a fresh detection months later.
    The backfill recomputes every row **from `raw_memo`**, never from the existing key, and rewrites rules by joining through the rows (old key → that row's `raw_memo` → new key) rather than by renormalizing the rule's own value. That is what makes it exact instead of dependent on idempotence — for every rule some surviving row still corroborates. There is one fallback: a rule whose key no current row carries has no rows to join through, so its own `match_value` is renormalized instead, which is exact only if that key is a fixed point. That is the one place the backfill stops being a join through the data and becomes a guess, so those rules are reported in their own `UNEVIDENCED REWRITES` section rather than folded into the rewrite count — with the genuinely broken sub-case marked `DRIFTS`, meaning the guess landed on a non-fixed-point key that no write path emits, so the rule is dead on arrival and needs retraining from a row. **"Retrain it from a row" is no longer unconditionally available** — as of v0.20.0 the Remember guard (rule 6) refuses a lossy or already-multi-category key, so a dead rule on such a key cannot be re-created through the UI at all. That is deliberate, not a regression: those are the keys no single exact rule can be right for. The `--apply` verification pass separately fails the run if any *row* is left unconverged.
    **Two tables key off this column, not one:** `category_rules.match_value` (for `match_type='exact'` only) and `subscription_dismissals.normalized_merchant`. Both carry unique indexes, so a rewrite that collapses two values collides, and in both tables the loser is **deleted**, not merely out-ranked. The two tables pick their survivor by deliberately opposite rules. For `category_rules` it is `compareRules`' own order (priority DESC, then **most recently updated**), because picking the oldest instead silently reverts the user's latest training. For `subscription_dismissals` it is the **oldest** `dismissed_at`, because there the earliest deliberate act is the one to preserve — a dismissal is a standing instruction, not a correction of an earlier one.
    The ranking models `buildRuleMatcher` as a whole — its skip filter as well as its sort. An archived category's rules never fire (rule 8 — inert, not deleted), so they sort **last** regardless of priority or recency; ranking one first would delete the live rule that was actually firing and keep one that never will, leaving the merchant with no effective rule at all. The printed collision lines mark them `(ARCHIVED — never fires)`.
    **A third consumer is not a table at all: the `?merchant=` URL param.** `/categorize`'s drilldown link filters `/transactions` on an EXACT `normalized_merchant` (`merchantDrilldownHref` → `loadTransactions`'s `eq()`), so a backfill that rewrites a key silently invalidates every link already built from the old one — a bookmark, or a URL shared into a note. Nothing in the database records that a link existed, so unlike the two tables above there is nothing for the backfill to rewrite and no collision to adjudicate; the coupling is real but one-way and unfixable from this side. It is handled at the destination instead: a `?merchant=` that matches nothing renders a zero-result state naming the key verbatim and offering `?search=<key>` as the recovery, which works precisely because `search` is `LIKE %x%` and case-insensitive where the merchant filter is neither. That recovery drops every OTHER active filter too, and truncates the key to `MAX_SEARCH_LENGTH`: keeping the other filters meant the suggested fix landed on a second empty page whenever a date range was what emptied the first, and `merchant` is deliberately unbounded while `search` is capped, so an over-long key turned the one offered escape hatch into a 404. `pageSize` is the one thing it does carry across, because it is a display preference rather than a predicate — it can never be why the list came back empty. That distinction is the same one `hasNonMerchantFilters` draws when it decides whether to blame the key: it excludes `pageSize` for that reason, and `includeTransfers` because that toggle only ever WIDENS the row set, so counting it made one click of "Show transfers" flip the empty state to "the merchant key itself may still be fine" on a page that had just gotten emptier for no new reason. Do not "fix" that empty state by widening the filter itself — the exactness is D2, and a `LIKE` drilldown returns a superset on 11 of 181 real groups.

    **A `contains`/`regex` rule is never rewritten but IS reported.** Its `match_value` is a substring or a pattern, not a key, so there is nothing to join through. The plan counts each one's reach against the old keys and the new ones and prints any that change, flagging a drop to zero as dead. That is reported, never refused: the normalizer change is what kills such a rule, at the moment it lands, so refusing would only withhold the repair for the rows.
    **A `contains` rule cannot be repaired by any backfill.** Its `match_value` is a substring, not a key. If a normalizer change stops that token appearing in any key, the rule is dead permanently — `AMAZON PRIME` and `GOOGLE ONE` were both one edit away from exactly that, saved by keeping `PRIME` out of `BRAND_QUALIFIERS` and adding `GOOGLE` to `PROCESSOR_PREFIXES`, not by the backfill. `normalize.test.ts` pins both tokens as reachable; treat that test as a contract with `drizzle/0006_subscription_rules.sql`.

11. **A value read before an `await` and used after it in a write is a PRECONDITION, not a fact — re-verify it inside the transaction that writes (v0.26.0).** `syncSimpleFin` reads the linked accounts, `await`s SimpleFIN, then inserts. `account.id` and its `simplefin_account_id` are carried across that boundary, and `setAccountLink` can commit in the window — both controls live on the same `/sync` page, so it takes two tabs and no crafted input. The result was not a duplicate but something neither dedup pass can see at all: feed A's rows filed under an account the user has just repointed, carrying feed A provenance — the misfiling class migration `0020` exists to prevent (rule 3), reintroduced as a race rather than as a schema mistake. **The vulnerable window is not the fetch.** It is read → write, which also spans the per-account staging loop and `createSnapshot`'s `VACUUM INTO`, and it is not bounded by `SYNC_TIMEOUT_MS` — that bounds the fetch alone, and only when the caller passes no signal of its own.
    `verifyStagedLinks` re-reads every staged account inside the write transaction and DROPS the ones whose link moved rather than failing the run: every other account was staged against a link that did not move, so refusing them would punish accounts that did nothing. Nothing is WRITTEN for a dropped account, so no dedup pass records the withheld rows and the drop is not destructive — but the warning is the entire mechanism that makes it non-silent, so the three cases carry three different REMEDIES rather than one reassurance. Repointed: sync again, and note that is advice rather than a guarantee — the next run stages the NEW feed's rows, which serve the withheld ones only if it is the same bank account behind a re-minted id. Unlinked: **link it again**, because an unlinked account falls out of the next run's `linked` query entirely, so "sync again" imports nothing for it and says nothing about it. Deleted: no remedy, and the warning offers none. An earlier draft folded the three together and told an unlinking user to sync again, which is a no-op that leaves the rows silently never arriving — a warning naming the wrong remedy is close to no guard at all. The per-account `counts` record is zeroed for a dropped account too, and in EVERY field rather than just `insertedCount`: the `duplicateBy*` figures counted matches against the old feed, and leaving `reportedBalanceCents` in place would have `finaliseBalances` subtract it from a ledger deliberately missing the withheld rows and report the difference as `driftCents` — rule 1's "a row is missing or duplicated" signal, manufactured. `skippedPending` is deliberately kept, because it is a fact about the PAYLOAD decided before any dedup pass touched the ledger, and its warning is withheld with the account's other staging notes so the two agree.
    **The idiom predates this release; what this release established is that fixing one such write does not close the CLASS.** `undoSyncBatch` already re-checks "still the newest batch" inside its own transaction rather than trusting the page's initial check (rule 5), and `anchorStartingBalance` runs inside `commitImport`'s transaction for the same family of reason (rule 1). Six review passes over the transaction-import fix each turned up a sibling the previous one had missed, all in the same function: the balance pass reading a link and a `hasAnyTransactionRows` answer from before the fetch (rule 1), `seenExternalIds` read in the staging loop and trusted after it (rule 3), `prior_starting_balance_*` taken from the pre-fetch account row (rule 9), and the empty batch minted when every account was withheld (rule 5). When you find one of these, enumerate every other value the function carries across the same `await` before calling it fixed.
    Two type-level guards exist so the property cannot be refactored away in silence, and neither is decoration. `SyncTx` is the handle `db.transaction()` hands its callback, and `verifyStagedLinks` takes THAT rather than `AnyDb`: typed loosely, "the re-read happens inside the write transaction" was enforced by a comment and one call site, so hoisting the call out for readability would compile, pass every test (a same-tick relink does not interleave under test), and reinstate the race. `_DB_IS_NOT_A_TX`/`_ANYDB_IS_NOT_A_TX` pin the assignability that argument rests on, because it is a property of drizzle's class hierarchy (`SQLiteTransaction`'s `protected` members) rather than of this file, and a dependency bump dropping those modifiers would take the guarantee away with `tsc` green. What neither guard covers: calling `verifyStagedLinks` in its own `db.transaction()` and inserting in a second one compiles and passes everything — it proves *a* transaction, not *the* one — which is tracked in TODOS.md rather than closed with a cast.

## Conventions

- Dates stored as ISO `YYYY-MM-DD` text. Timestamps as Unix seconds (`integer` with `mode: 'timestamp'`).
- Booleans as `integer` with `mode: 'boolean'`.
- Enum-like text columns use `text('col', { enum: [...] })` so Drizzle type-narrows.
- Foreign keys: always declare `references(() => ...)` on the column. Use `onDelete: 'restrict'` by default; explicit `'cascade'` where it makes sense (e.g. `category_rules` → `categories`).
- Merchant normalization is a pure function in `src/lib/normalize.ts`, a four-phase pipeline (leading noise -> reference tokens -> trailing noise -> location/tail). Ordering is load-bearing at the 1-before-2 and 3-before-4 boundaries **and within a phase** — phase 3's phone rule has to precede `TRAILING_STATE`, because it matches the trailing state code as part of its own pattern; swapping just those two statements fails seven tests. Treat every ordering there as load-bearing unless a test says otherwise. Phases 3+4 run to a fixed point (capped at 8 passes), which together with the `TRAILING_STATE` allowlist is what makes the function idempotent. Two known exceptions, both pinned in the tests: a key that still contains a `*`, and a memo carrying more than one embedded timestamp. Tested in isolation. See `.context/csv-format.md`.
- **`PROCESSOR_PREFIXES` and `BRAND_QUALIFIERS` carry opposite risks; do not extend them with the same confidence.** A processor MISSING from the set collapses every merchant behind it into one bucket (the reason `GOOGLE` had to be added: Google One and YouTube Premium shared one key that spanned two categories), so an extra entry there is cheap. A `BRAND_QUALIFIERS` entry is DESTRUCTIVE in the other direction — it silently eats a trailing word off a real merchant name — so that list is evidence-only and currently holds exactly one entry. `TRAILING_STATE` is an allowlist for the same reason: as a bare `[A-Z]{2}` it also ate genuine bank-truncated suffixes (`TAPPED APPLE LL` → `TAPPED APPLE`) on a second pass.
- Subscription detection excludes rows where `raw_description = 'DEPOSIT'` or `raw_memo` starts with `POS ` + digits (those are refunds, never recurring).

## Automated sync (SimpleFIN)

`/sync` pulls posted transactions from Star One via SimpleFIN and writes them straight in — no preview step — behind a pre-write snapshot and a per-batch undo. Credentials live in `SIMPLEFIN_ACCESS_URL` in `.env.local` (gitignored); only the host is ever safe to display. That rule is enforced, not remembered: `authHeader` is a `Secret` whose `toString`/`toJSON`/inspect hooks all return `[redacted]`, so reading it takes an explicit `.expose()`.

The feed response is parsed with a zod schema in `client.ts`, never cast. It is the only untrusted input in the app, and an unchecked cast let a shape change through as `undefined` fields that the downstream `?? []` fallbacks read as "no accounts" — reporting a clean "up to date" while importing nothing. Schemas are `looseObject`, so a field MX adds later is not a hard failure.

Every `/sync` server action returns its outcome as state rather than throwing (`src/app/sync/error.tsx` is the backstop). Several failures are reachable from ordinary use — a stale tab resolving a bucket another tab already resolved, a double-submitted undo — and a throw would take out the undo button and the balance check along with the page.

**That includes the REVALIDATION, which is not obvious and was got wrong twice.** `revalidateAll()` must run AFTER the write's `try` — inside it, a throw from `revalidatePath` reports an already-committed row as a refusal. But merely moving it out is only half a fix: the throw then escapes the action entirely, and `error.tsx`'s copy affirmatively promises "Nothing was imported. Your ledger is unchanged", which is false once the write has landed and is the more misleading of the two failures. So the refresh is guarded on its own (`guardRefresh`) and a failure comes back as a WARNING folded into the already-successful outcome, plus a `console.error` — the write is durable at that point, and a stale page with an accurate message beats a crash with a false one. `revalidateAll()` therefore returns `string[]`, not `void`: a caller that drops the result makes a failed refresh silent again.

**As of v0.27.0 this is ONE function, applied everywhere, and that is the point.** `guardRefresh(scope, run)` (`src/lib/revalidateAfterWrite.ts`) is the single spelling. It was two hand-maintained copies — `/sync`'s and `/budget`'s `guardBudgetRefresh`, added in v0.26.0 — which had already drifted on the warning wording, while the other **six** route action files had none at all: 47 unguarded `revalidatePath` calls after committed writes (accounts 4, categorize 6, goals 6, import 5, subscriptions 6, transactions 20 — counted as call expressions; three of them sit in `for` loops over path arrays, so the number of PATHS is higher). That is rule 11's own lesson in a different guise (fixing one instance does not close the class), one release later, so the answer was one function rather than an eighth copy. It lives outside every `"use server"` module because such a module may only export async functions — an exported const beside an action makes Turbopack report "the module has no exports at all" and every importer of every action in that file fails to resolve, blanking the route, with `tsc` and vitest both structurally blind to it (a bundler rule, not a type rule; it surfaces only by loading the page). Three instances were worse than a stale page. On **`/accounts`**, every action wraps its whole body — the refresh included — in one `try` whose `catch` returns `fail(...)`, so a committed reconcile reported as failed, the user resubmitted, and the second write took its `prior_starting_balance_cents` from the row the first had already changed: rule 9's single undo slot spent on a figure that was never current, which is the harm rule 1 documents for the feed balance pass, reached through the refresh instead of a race. On **`/import`**, `confirmImportAction` commits the batch, the rows and the snapshot and deletes the pending import before revalidating, so a throw rendered the boundary for the page that form is submitted from — `import/preview/[id]/error.tsx`, NOT `import/error.tsx`, which this doc named for a release — whose copy is "Nothing was written — a preview is read-only. Committing the import (a separate step) is the only action that writes rows, and it snapshots the database first": every word false several hundred rows in, and the "separate step" it sends the reader to is the one that already ran. (`import/error.tsx`'s "Nothing was imported" is the boundary for `updateAccountAnchorAction`, whose form does render on `/import`.) On **`/categorize`, `/transactions` and `/subscriptions`**, the refresh runs BEFORE the undo snapshot is returned, and those writes can already have DELETED a trained rule (rule 6), so a throw discarded the snapshot and rendered "Categorize failed." for a committed write whose only 10-second way back never appeared. A failure now comes back as a WARNING folded into the successful outcome; `/sync`'s doctrine holds, so a warning is never rendered as a plain success (`role="alert"`, `toast.warning`, merged into the single toast rule 6 requires rather than stacked). **`redirect` signals by THROWING, and a bare `catch` here would swallow the navigation and hand back a warning string instead.** On `confirmImportAction` that is a committed several-hundred-row import whose redirect silently vanishes, with no state channel to notice it (`Promise<void>`). Five call sites keep their `redirect` outside `run` by hand, but rule 11 is explicit that a property defended by prose is a property waiting to be refactored away — so `guardRefresh` calls `unstable_rethrow` before it decides anything, which re-throws exactly Next's control-flow signals (`redirect`, `notFound`, the dynamic bailouts) and returns for everything else. The hand placement is now belt-and-braces rather than the only defence, and it is pinned by a test either way.

**Two things travel with the function rather than in it.** The SENTENCE is a constant in `src/lib/refreshWarning.ts`, which has zero imports — `revalidateAfterWrite.ts` no longer does, and `_month-editor.tsx` is a client component that needs the sentence without dragging `next/navigation` into its bundle (the measured +376 KB `limits.ts` shape). The RENDERING is `src/components/ledger/action-status.tsx`, after four hand-rolled copies of one decision inside the branch whose whole subject is that hand-maintained copies drift: `role="alert"` for a refusal AND for a warning, `status` only for a plain success, because a polite live region can be held until the user goes idle and the warning is the case where that costs the most — it says the write LANDED, and a user who does not hear it resubmits, which under rule 9 spends the account's one `prior_starting_balance_*` slot on a value that was never current. A warned success is still toned `ledger`, not `redbrown`: the message is reporting a write that landed, and the amber block beneath it carries the signal.

**A refusal must be returned BEFORE the refresh, in every action.** Four places got this wrong (`nothing-to-undo`, `stale`, `already-unpaired`, `no-linked-accounts`); all four wrote nothing, so revalidating was not merely wasted — it re-renders the form holding the inline `role="alert"` out from under the only rendering of that refusal. `syncNowAction`'s was the one that survived two review passes, because `SyncButton` renders at a fixed position and never unmounts, so it does not lose its own message; it is a trap for whoever next moves that button into a conditional section rather than a live bug.

**A no-op is never reported as a completed action** — but `ok` and `fail` are not interchangeable for it. `nothing-to-undo` and `already-unpaired` return `fail`, because a durable fact the user asked for is MISSING (no rows deleted, no "not a transfer" recorded). `linkAccountAction`'s no-op re-save returns `ok` with different copy, because the end state IS what was asked for — it just already held. `setAccountLink` returns `linkChanged` for this; the caller cannot re-derive it, since by the time it sees the result the UPDATE has landed and the prior value is gone. The same doctrine is why a run whose accounts were ALL withheld reports `up-to-date` rather than `synced` (rule 11 — nothing was written, so there is no batch and nothing for `/import` to show), and why the balance pass reports only the updates that actually wrote (rule 1). A warning is not a success either: `ActionStatus` renders `role="alert"` for anything that is not a plain `ok`, because the sync warnings include "its transactions were not imported" for an account whose link moved mid-run, and a polite live region can be held until the user goes idle.

Constraints that are properties of the feed, not choices:

- **Never more than ~45 days of history.** SimpleFIN hard-caps at 90 days — corroborated by the feed's own error string, "Requested date range exceeds limit of 90 days and was capped." The 45 is *our* conservative halving, not a documented provider limit; don't restate it elsewhere as a quoted SimpleFIN rule. CSV import stays the only path to anything older — it is not legacy.
- **No pending transactions**, and this is now *enforced* rather than assumed. Star One via MX exposes posted rows only, and sync never requests them — but that is an observation about one institution at one time. Any row arriving with `pending: true` is skipped, counted into `skippedPending` and warned about, because writing one is the worst outcome available: dedup keys on `external_id`, SimpleFIN may change that id when the row posts, and there is no update path — so the pre-auth amount would freeze *and* the posted row would land beside it. Pending activity stays visible as the gap between `balance` and `available-balance`.
- **Accounts must be linked explicitly** (`accounts.simplefin_account_id`). The feed also returns a mortgage, which the `checking|savings` enum does not model; unlinked means never imported.
- **`description === memo` on every row**, so `raw_description` has no source field and is derived from the sign. This keeps the subscription-detection exclusion on `raw_description = 'DEPOSIT'` working.
- Amounts are decimal strings — parse via `parseAmountToCents` (string math), never `parseFloat(x) * 100`.
- `normalizeMerchant` needs no SimpleFIN-specific rules: the feed's `description` is byte-identical in shape to the CSV `Memo` column, so trained `category_rules` keep matching. MX's cleaned `payee` is persisted to `transactions.payee` for display only — categorization keys on `normalized_merchant`, never on `payee`, or every trained rule would break. NULL on CSV rows.

## What's NOT in V1 — do not add

Auth. Cloud sync. Multi-currency. Bill pay. Investment tracking. Tax features. Split transactions (one category per transaction; override wins). Retroactive goal target edits. YNAB-style overspend-shuffle. Cloud/NAS hosting (Docker exists for local self-hosting only — see `docs/plans/dockerize-postgres.md`, PR3). Tests for UI components (categorization logic only).

**Credit cards and loans came IN as of v0.16.0** and are no longer on this list. What stayed out of that feature, deliberately, is worth naming because it looks like an omission otherwise: no interest or APR modeling, no payoff projection, no minimum-payment tracking beyond storing the number for reference, no statement periods or due dates, and no balance history series (`accounts.prior_starting_balance_cents` holds exactly one prior value, not a series — a debt trend line is unbuildable until that changes; see TODOS.md). **And no card TRANSACTION import, which is the exclusion most easily mistaken for a gap rather than a decision:** `partitionLinkedAccounts` routes every `accountClass(type) === 'liability'` account into `balanceOnlyAccounts`, so a sync fetches a card's or a loan's **balance** and stages **none** of its transactions — E1, and load-bearing (importing a mortgage's interest/escrow/principal rows double-counts a payment already budgeted on the checking side, and it was self-disabling, since once the loan had rows the zero-row-scoped balance pass skipped it forever). This is what makes "the feed keeps the card's balance current" and "card spending reaches an envelope" mutually exclusive, and 1.0.0 picks the first (PLAN.md, the anchor-only decision of 2026-09-09). Do not answer "will my card transactions arrive on the next sync?" with yes. A mortgage is deliberately quiet: muted money weight, grouped under `LONG-TERM`, no utilization bar, no hand-entered charges, and no paid-down line until it has rows — because it is a fact about your life rather than a problem you are solving this month. It **does** still get a balance control (Reconcile, or Refresh when it is feed-linked with no rows); see rule 9 for why gating that on type was tried and reverted.

**Automatic same-account reversal detection is out, permanently, and not for lack of effort (v0.19.0).** `/sync`'s reversal queue finds the candidates and links none of them; the pairing is always a human's call. Roughly 13% of the shape is coincidence on real data and a wrong link deletes real spending from every spending surface with no error, so there is no threshold at which auto-linking is the right trade here. Read rule 4 before proposing a heuristic for it.
